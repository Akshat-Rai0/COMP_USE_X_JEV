How it should work

A task is a loop of small steps. Every step makes the same five moves: look, describe, decide, act, check.

"Jev" below is shorthand for whichever decision backend is active. Most weeks that is kev, a small local model serving the same typed-question contract; real Jev is swapped in the moment access arrives. See System wiring for the interface and the differences between them.

The analogy. A driver at a junction. Eyes take in the scene, the mind names what matters, a trained reflex picks the turn, hands turn the wheel, and a glance in the mirror confirms the car went where intended. A navigator in the passenger seat only speaks up when the driver is unsure.

One step, in order

  1. Look
    Cua Driver reads the UI element tree of the front window. It also saves a screenshot, used only for the log and for escalations to the LLM.
  2. Describe
    The serializer turns the tree into short numbered lines such as e17 button "Add reminder" and keeps the most relevant elements, at most 255, so one Choice question can cover them.
  3. Decide
    One Jev request carries the state plus several small questions. Choice asks which element to act on next. Noul asks yes-or-no questions such as "is the goal reached" and "is an error visible". Jev answers them in parallel with probabilities, and a confidence value for each Choice.
  4. Act
    If the answer clears the gates below, the Driver clicks or types on that element. If not, the step escalates to the planner.
  5. Check
    After the screen settles, the next pass asks a Noul question: did the intended change happen? If it did not happen twice in a row, the planner replans.

Voice as a second input channel

Push-to-talk speech, transcribed locally, can do two things: start a new task, or interrupt a running one with a correction. It never becomes a new kind of decision-maker. A transcript is just text, and text already has a place in this loop: it goes wherever task already goes, or into planner.replan() as a correction.

The analogy. A passenger who can say "turn left" at a red light, never while the car is mid-turn. The only safe moment to listen for a correction is the same place the loop already pauses to look at the road: the top of the loop, between Check and the next Decide.

  • No run active: a push-to-talk transcript becomes task, exactly like typed input. The loop starts as usual.
  • A run is active: the transcript is queued, never applied mid-step. At the top of the next iteration, the loop drains the queue, sends the transcript to planner.replan() as a correction alongside the current screen and history, and continues with the revised plan.
  • A risky action is pending approval: a spoken correction can redirect or cancel, but it can never itself approve the pending action. The click-to-approve gate stays in force no matter which input channel produced the plan. This is a fixed rule in code, not a confidence threshold, so it holds even if the correction sounds unambiguous.

Nothing else changes. The mic thread only ever writes to a small queue; it never calls body.act(), never touches the gates, and never talks to the decision backend directly. One optional field is added to StepRecord: interrupt, present only on a step where a queued correction was applied.

The loop in raw code

Open the full loop

backend.decide stands in for the Jev request. The real request and response shape comes from the Jev Quick Start; confirm it in week 1. The loop uses plain loops and lists so every state is easy to trace by hand.

def run_task(task, body, backend, planner, limits):
    plan = planner.make_plan(task)              # LLM, once per task
    history = []
    seen_screens = {}
    failed_in_a_row = 0
    step_number = 0

    while step_number < limits.max_steps:
        step_number = step_number + 1

        # Voice interrupt (checked only here, never mid-step)
        interrupt_record = None
        if voice.has_pending_command():
            correction = voice.pop_pending_command()
            window_for_replan = body.read_frontmost_window()
            plan = planner.replan(task, window_for_replan, history, correction=correction)
            interrupt_record = {"source": "voice", "transcript": correction}
            # Note: this cannot approve a pending risky action.
            # The approval gate below is still checked normally on this
            # step's own action, whatever the new plan proposes.

        # Look and describe (Body)
        window = body.read_frontmost_window()
        elements = serialize_and_prune(window, max_elements=255)
        screen_id = hash_screen(elements)

        if screen_id in seen_screens:
            seen_screens[screen_id] = seen_screens[screen_id] + 1
        else:
            seen_screens[screen_id] = 1

        if seen_screens[screen_id] >= 3:        # loop breaker
            plan = planner.replan(task, window, history)
            seen_screens = {}
            continue

        # Decide (Reflex): several small questions in one request
        questions = []
        questions.append(Choice("next_element", elements))
        questions.append(Noul("goal_reached", plan.goal_statement))
        questions.append(Noul("error_visible", "An error dialog is visible"))
        if len(history) > 0:
            questions.append(Noul("last_action_worked", describe_intended_effect(history[-1])))

        state_text = build_state_text(task, plan, elements, history)
        answers = backend.decide(state=state_text, questions=questions)

        # Check (Verify)
        if answers.noul("goal_reached") >= 0.90:
            return finish(task, history, "goal reached, awaiting code check")

        if answers.noul("error_visible") >= 0.80:
            plan = planner.replan(task, window, history)
            continue

        if len(history) > 0:
            if answers.noul("last_action_worked") < 0.50:
                failed_in_a_row = failed_in_a_row + 1
            else:
                failed_in_a_row = 0
            if failed_in_a_row >= 2:
                plan = planner.replan(task, window, history)
                failed_in_a_row = 0
                continue

        # Gates
        choice = answers.choice("next_element")
        top_two_gap = choice.top_probability - choice.second_probability
        sure_enough = False
        if choice.confidence >= limits.confidence_gate:
            if top_two_gap >= limits.min_gap:
                sure_enough = True

        if sure_enough:
            element = choice.value
            decided_by = "jev"
        else:
            element = planner.pick_element(task, plan, elements, window.screenshot)
            decided_by = "llm"
            if element is None:
                return ask_human(task, history, "planner also unsure")

        action = action_for(element, plan)        # click, type, or press
        if is_risky(action):
            if not human_approves(action):
                return finish(task, history, "stopped by human")

        text_value = None
        if action.kind == "type":
            text_value = planner.write_text(task, plan, element)

        # Act (Body)
        body.act(element, action, text_value)
        history.append(record_step(step_number, decided_by, answers, element, action, interrupt=interrupt_record))
        body.wait_until_settled()

    return finish(task, history, "step limit reached")

When things go wrong

SituationWhat should happen
The app exposes little or nothing in its UI treeThe step goes to the planner with the screenshot. If a whole app behaves this way it cannot be the hero task
The screen is still animating when readRead again until two reads match, with a time limit
Jev picks the wrong control with high confidenceThe next Noul check should catch it. Every such case is counted in the calibration table
Jev says the goal is reached but it is notFinal success is decided by a code check on the real end state, never by Jev alone
An API call times outOne retry, then escalate the step. Three timeouts in a row stop the run

Safety rules that never depend on a model

  • The agent runs in a dedicated macOS user (later possibly a VM) with no personal accounts signed in.
  • Only allowlisted apps can be controlled.
  • Deleting, overwriting, sending, and buying always need a human click — a spoken correction can redirect or cancel, but it can never itself approve a risky action.
  • A kill switch stops the run within one step. Limits on steps, time, and cost are hard caps.
  • API keys live only in the orchestrator process, never in the sandbox.
