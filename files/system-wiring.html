The four layers

  • Body
    Cua Driver reads the screen and acts
  • Reflex
    Jev picks the next control
  • Planner
    An LLM plans, writes text, and rescues
  • Verify
    Noul questions check the result

System wiring

One Python orchestrator owns the loop, the keys, and the trace. It talks to the Body inside a sandbox, to a swappable decision backend, and to a planner LLM.

What one step records

StepRecord, a proposed shape

Field names are a proposal. Every model and driver version is recorded as an exact string, never as "latest". backend is "jev", "kev", or "llm", whichever answered this step. interrupt is null on almost every step; it is only set to {"source": "voice", "transcript": "..."} on the one step where a queued correction was drained and applied.

Caveats found in the architecture check

These are the things most likely to bite later. The Roadmap says which week resolves each one.

IDCaveatWhat the wiring does about it
C1Jev is early access with a waitlist. No key means no project.The decision backend is an interface with three implementations: Jev; kev (jaredpalmer/kev), a small pre-trained local model that serves the identical POST /v1/systemone contract, so TypeSafe's own SDK works against it with only a base_url change; and an LLM wrapped to return the same typed answers. Everything else can be built, and the full loop tested end to end, before Jev access arrives.
C2Jev's published demos take text state, not images. The Driver must yield a usable UI tree, and some apps expose very little.A week 1 to 2 spike rates candidate apps. Screenshots go only to the planner fallback. Cua's licence notes mention OmniParser and an optional cua-agent[omni] extra that includes an AGPL-licensed dependency, so avoid it unless truly needed.
C3A Choice question covers at most 255 options. Real UI trees are larger.The serializer prunes and ranks. Score questions are one way to rank; the per-request question limit needs confirming. Beyond 255, use the two-stage approach TypeSafe describes: score, then choose.
C4Jev answers one request at a time, remembers nothing, and cannot write text.The controller puts a short history into each state. Planning and typed values stay with the LLM.
C5Speed claims come from TypeSafe's US West Coast laptops. A round trip from Patna will be longer.Measure p50 and p95 in week 1. Pack all questions for a step into one request. Set a per-call timeout.
C6macOS grants Accessibility and Screen Recording to an app identity, not a file path. Cua documents a raw driver daemon started outside CuaDriver.app as unsupported.Use the installed CuaDriver.app and its daemon. Never grant permissions to loose binaries. Run cua-driver doctor in week 0 and test launching from Python in week 1.
C7The Driver's SDK contract is marked experimental and the repo moves fast.Pin the Cua release, hide every call behind the Body adapter, and test the loop against a fake Body.
C8Model aliases can drift. "Latest" may change behaviour between runs.Pin the exact Jev version string, store it in every StepRecord, and rerun the baseline if it changes.
C9The agent controls a real Mac and holds API keys.Sandbox user, app allowlist, approval gate, kill switch, hard budgets. Keys live only in the orchestrator.
C10Vendor numbers are not your numbers. TypeSafe's speed and accuracy figures come from its own evaluations.Measure on the hero task, publish the calibration table, and judge final success by a code check, not by Jev.
C11Licences and terms. Cua is MIT, but extras have other licences. TypeSafe's terms on publishing benchmark results are unread.Read the terms in week 0. Keep AGPL extras out of the repo.
C12Voice is a second input channel that can reach a running loop. If it is read at the wrong moment it could apply a correction mid-action, or a spoken phrase could be mistaken for approval of a risky action.The mic thread only writes to a queue; the loop controller drains it at one fixed point, between the check and the next decide, never mid-step. The risk gate is a fixed rule in code that voice cannot satisfy: a risky action always needs a UI click, whatever the transcript says.
C13kev is a 0.5B-parameter stand-in, not a copy of Jev. Its own evaluation shows it is untrained on tasks far from passage classification, its context caps at 8,192 tokens against Jev's roughly 32k per branch, and it can lose to Jev on knowledge-heavy picks (its own example: choosing return_policy over return_status). It is also a single-author project with no fine-tuning applied for this project's task.Treat kev as a development and testing stand-in only, never as the number reported in the final calibration table. Every number that matters for the write-up is measured on real Jev once access arrives. If kev's accuracy on the actual UI-tree Choice questions looks weak in the week 1 to 2 spike, its own training recipe is a documented stretch goal, not a requirement.
